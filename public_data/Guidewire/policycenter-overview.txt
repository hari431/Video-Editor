POLICYCENTER OVERVIEW
=====================

PolicyCenter is Guidewire's policy administration product for managing insurance policy lifecycles. Public documentation describes policy transactions such as submissions, renewals, audits, policy changes, cancellations, reinstatements and rewrites.

CORE MODEL
----------
A policy is not changed arbitrarily. Policy changes are represented through transaction/job concepts. The transaction captures the work required to move from one policy state or term to another.

BUSINESS PERSPECTIVE
--------------------
PolicyCenter sits in the policy administration layer and commonly interacts with systems such as billing, claims, rating, document services and external data providers.

CLOUD PERSPECTIVE
-----------------
Current Guidewire Cloud documentation exposes PolicyCenter functionality through Cloud APIs. The current documentation describes policy transactions as Job resources for many workflows.

POLICY PERIOD AND BUNDLE MODEL
------------------------------
Every Policy has one or more PolicyPeriod branches. Only one branch is bound at a time. Edits happen inside a gw.transaction.Transaction bundle; the bundle isolates writes until commit. A Period holds effective dates, rating data, and references to coverages. Creating a PolicyChange means opening a new Period branch from the bound Period, editing inside a bundle, then completing the Job.

GOSU QUERY EXAMPLE
------------------
Gosu uses the Query API for strongly typed searches. Finding a bound PolicyPeriod by policy number:

uses gw.api.database.Query
uses gw.api.database.Relop

var periods = Query.make(entity.PolicyPeriod)
  .compare(PolicyPeriod#PolicyNumber, Relop.Equals, "123456")
  .compare(PolicyPeriod#Bound, Relop.Equals, true)
  .select()

For a single result, use `Query.make(PolicyPeriod)...select().first()`. Always filter by `Bound` and `MostRecentModel` when querying the operational table; otherwise you may retrieve multiple branches for the same policy number.

JOB TYPES AND LIFECYCLE
-----------------------
PolicyCenter models each business action as a Job with a specific subtype. The subtype determines required related entities and validation.

Job Type              Typical Trigger               Key Related Entity
Submission            New business request           Policy → Job → Period (TC_SUBMISSION)
PolicyChange          Mid-term endorsement           Period (branch from bound)
Renewal               Term expiration                Period generated before expiration
Cancellation          User or system cancel          Cancellation entity + Period
Reinstatement         Reversing a cancellation       References prior Cancellation
Rewrite               Replacing a policy with new terms  New Policy linked to prior Policy
Audit                 Exposure true-up               Audit entity + Period

A Job moves through Draft → Quoted → Bound (or Closed/Declined). Quote, preemption, andUW-issue handling occur before Bound. Freezing a quoted branch before effective-date conflicts is part of out-of-sequence handling.

COMMON TECHNICAL PITFALLS
-------------------------
Treating Policy as the mutable record instead of Period; querying without `Bound = true` and therefore mixing draft branches; modifying a Period outside a bundle and expecting commit; copying an endpoint from an old PolicyCenter release without checking the release-specific Cloud API reference for Job resources.

PRACTICAL LEARNING PATH
-----------------------
Learn insurance concepts first, then accounts/policies/jobs, then transaction-specific flows, then product/rating, activities/underwriting, integrations and APIs.

KEY TAKEAWAYS
-------------
PolicyCenter is best understood as an insurance transaction platform, not simply a database of policies.
