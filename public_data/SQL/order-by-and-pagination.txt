ORDER BY AND PAGINATION
=======================

Sorting results and segmenting them into pages (pagination) are fundamental operations in application development. Proper pagination guarantees that databases do not consume excessive memory buffering huge result sets, while ensuring responsive, low-latency performance for the end user.

DETERMINISTIC ORDER
-------------------
To make pagination stable and repeatable, your ORDER BY clause must be fully deterministic. If a query orders records by a non-unique field (such as 'created_at', 'status', or 'last_name') without a unique tie-breaker, the database engine is free to return rows in any physical order during consecutive page fetches. This can cause rows to mysteriously shift between pages, appearing duplicated or disappearing entirely from the user's perspective.

-- ❌ INSECURE PAGINATION (Non-deterministic sorting)
SELECT id, status, created_at
FROM claims
ORDER BY created_at DESC
LIMIT 10 OFFSET 20;

-- ✅ SECURE DETERMINISTIC PAGINATION (Adding a unique primary key tie-breaker)
SELECT id, status, created_at
FROM claims
ORDER BY created_at DESC, id DESC
LIMIT 10 OFFSET 20;

PAGINATION STRATEGIES
---------------------
There are two primary industry strategies for implementing database pagination, each with distinct performance characteristics and engineering trade-offs:

1. Offset Pagination (OFFSET and LIMIT)
Offset pagination skips a specified number of records using the OFFSET keyword, then returns the subsequent limit. It is extremely simple to implement and natively supports direct navigation to arbitrary page numbers (e.g. "Go to Page 15").

However, Offset pagination does not scale for large tables or deep pages. Under the hood, the database cannot simply jump to the offset index; it must scan, load, and sort all preceding N records, only to discard them and return the requested limit.
- Time Complexity: O(N) where N is the offset depth.
- Performance Profile: Deep pages (high offsets) suffer from extreme latency spikes and high disk/I/O cost.

2. Keyset / Seek Pagination (The Cursor Method)
Keyset pagination avoids the OFFSET keyword entirely. Instead, the application passes a "cursor" representing the values of the sort keys from the last record of the previous page. The query uses a WHERE predicate to locate records that fall sequentially after that cursor.

-- Fetching the first page
SELECT id, created_at, total_premium
FROM policies
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Let's assume the last record has created_at = '2026-09-30' and id = 5894

-- Keyset Query for the second page (fetching rows older/lower than the last seen cursor)
SELECT id, created_at, total_premium
FROM policies
WHERE (created_at < '2026-09-30') 
   OR (created_at = '2026-09-30' AND id < 5894)
ORDER BY created_at DESC, id DESC
LIMIT 20;

- Time Complexity: O(log N) if appropriate composite indexes are in place.
- Performance Profile: Consistent, lightning-fast response times regardless of page depth because the query navigates directly via index structures.

COMPARING STRATEGIES
--------------------
| Feature | Offset Pagination | Keyset / Seek Pagination |
| :--- | :--- | :--- |
| **Ease of Use** | Extremely High | Moderate (requires cursor handling) |
| **Arbitrary Jumps**| Supported natively | Not supported (sequential only) |
| **Performance** | Degrading: O(N) scan time | Constant: O(log N) index seek time |
| **Dynamic Drifts** | High risk of duplicate/skipped rows | Resilient to concurrent inserts/deletes |

COMMON MISTAKES
---------------
1. Relying on Natural Table Order: Assuming that rows are implicitly returned in insert order if ORDER BY is omitted. Relational theory states that table records are unordered bags of data. Without explicit sorting, physical scans can return any sequence.
2. Inefficient Indexing: Implementing seek pagination without a composite index matching the seek columns (e.g., an index on `(created_at, id)`). Without this index, the database reverts to expensive full-table scans.
3. High Offset Exhaustion: Allocating arbitrary deep navigation buttons in customer-facing frontends without limiting max query offsets, leaving the database vulnerable to resource exhaustion attacks.

KEY TAKEAWAYS
-------------
- Deterministic ordering with unique tie-breaker columns is required for stable, duplication-free pagination.
- OFFSET-based pagination is ideal for small datasets or limited page depths, but fails to scale on large enterprise tables.
- Seek/Keyset pagination is the gold standard for high-volume infinite scrolling, transaction logs, and real-time activity feeds.
