RELATIONAL DESIGN: DATABASE NORMALIZATION & CONSTRAINTS
=====================================================

Relational database design relies on two main pillars to guarantee data integrity, consistency, and performance: Normalization (logical design) and Constraints (physical design). Together, they eliminate data redundancy and prevent operational anomalies that could corrupt system state.

THE OBJECTIVES OF NORMALIZATION & DATA INTEGRITY
------------------------------------------------
Normalization is the process of organizing columns and tables in a relational database to reduce duplication. By separating distinct facts into distinct tables, normalization prevents the three types of write anomalies:
1. Insert Anomaly: The inability to add a fact because other unrelated data is missing (e.g., being unable to register a new Customer because they have not purchased a Policy yet, if both are stored in a single table).
2. Update Anomaly: If customer details are duplicated across multiple policy rows, changing a phone number requires updating dozens of rows. If one row is missed, data becomes inconsistent.
3. Delete Anomaly: Deleting a record unintentionally destroys other unrelated facts (e.g. canceling a Policy deletes the entire customer profile because they were stored in the same table row).

DEEP DIVE INTO NORMAL FORMS
---------------------------
Relational theory defines several progressive levels of normalization, known as Normal Forms:

- First Normal Form (1NF): Requires that all table columns hold atomic, indivisible values, and that there are no repeating groups or multi-valued columns (e.g., storing a comma-separated list of telephone numbers in a single `phone_numbers` text field violates 1NF).
- Second Normal Form (2NF): Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key. This is only relevant for composite keys. If a table has a composite key of `(Policy_ID, Broker_ID)`, any column that depends only on `Broker_ID` (such as `Broker_Email`) violates 2NF and must be moved to a separate `Brokers` table.
- Third Normal Form (3NF): Must be in 2NF, and there must be no transitive dependencies. A transitive dependency occurs when a non-key column depends on another non-key column, which then depends on the primary key (e.g., `Policy_ID` (Key) -> `Customer_ID` -> `Customer_Zip_Code`. Here, ZIP code depends on `Customer_ID` rather than `Policy_ID`; hence, it must be moved to a separate `Customers` table to satisfy 3NF).

PHYSICAL INTEGRITY ENFORCEMENT: DATABASE CONSTRAINTS
----------------------------------------------------
Constraints are declarative rules defined on a database schema that structurally enforce data integrity. They prevent invalid data from being inserted at the engine level, acting as the absolute last line of defense:

1. Primary Key (PK): Uniquely identifies each row in a table. It cannot contain NULL values and must be indexed (typically a B-tree).
2. Foreign Key (FK): Establishes and enforces a relationship between two tables. It ensures that values in a column must match a valid primary key in the parent table, blocking orphaned child records and enforcing referential integrity.
3. Unique Constraint: Guarantees that all values in a column or set of columns are unique across the entire table (e.g. an `email` or `tax_id` column), allowing NULL values in some databases.
4. CHECK Constraint: Enforces domain-specific logical checks on a column before write confirmation (e.g., `CHECK (age >= 18)` or `CHECK (premium_amount > 0.00)`).

DENORMALIZATION: PRAGMATIC WORKLOAD TRADE-OFFS
----------------------------------------------
While normalization guarantees consistency and saves write overhead, it comes at a read cost: assembling normalized data requires performing relational joins (`JOIN` operations), which are computationally expensive on high-volume tables.

In read-heavy workloads (such as Data Warehouses, OLAP systems, or reporting dashboards), designers deliberately "denormalize" data. This involves duplicating specific columns (e.g. writing the customer's name directly inside the policy transaction ledger) to bypass joins and enable single-index scans.
- Trade-off: Denormalization accelerates reads but slows down writes, increases disk storage, and requires an active strategy (e.g., database triggers or overnight batch syncs) to ensure duplicated data remains consistent.

COMMON MISTAKES
---------------
- Normalizing to the Extreme: Purposely splitting tables into dozens of tiny relations for small datasets. This results in incredibly nested queries with 15+ joins, degrading CPU efficiency and database optimizer planners.
- Skipping Foreign Keys for "Performance": Omitting foreign key constraints under the false assumption that constraints slow down writes. In reality, the referential integrity check is highly optimized, and skipping it risks corrupting your entire data model with orphaned rows.
- Storing List Strings: Storing JSON strings or comma-separated lists inside VARCHAR columns instead of establishing proper parent-child relations. This prevents indexing and blocks relational aggregation.

KEY TAKEAWAYS
-------------
- Normalization (1NF, 2NF, 3NF) systematically eliminates redundancy and write anomalies.
- Constraints (Primary Key, Foreign Key, Unique, CHECK) physically enforce referential and domain integrity.
- Denormalize selectively and consciously for performance optimization, with a clear strategy to reconcile duplicated data.
